## Контекст

Мы хотим сделать максимально простой consumer VPN-сервис, ориентированный прежде всего на пользователя смартфона.

Главный принцип:

**мы НЕ разрабатываем собственное VPN-приложение на первом этапе.**

В качестве клиентского приложения предварительно выбрали **INCY**.

INCY устанавливается пользователем отдельно из App Store / Google Play и используется только как клиент для подключения к **нашей инфраструктуре**.

То есть:

```text
Пользователь
↓
наш сайт
↓
получает доступ
↓
скачивает INCY
↓
импортирует нашу персональную подписку
↓
INCY
↓
наш VPN-сервер
↓
интернет
```

INCY не является нашим VPN-провайдером и не должен быть промежуточным сервером для пользовательского трафика. Это только приложение-клиент.

# Что уже решили

### 1. Основной интерфейс — сайт

Мы хотим строить продукт прежде всего вокруг сайта, а не Telegram-бота.

На сайте пользователь должен иметь возможность:

- понять продукт;
- начать trial;
- зарегистрироваться / идентифицироваться;
- скачать INCY;
- получить свой VPN-доступ;
- оплатить подписку;
- увидеть состояние подписки;
- получить реферальную ссылку;
- при необходимости восстановить доступ / инструкцию.

Telegram в будущем можно использовать для:

- авторизации;
- поддержки;
- уведомлений;
- новостей;

но он не должен быть обязательной частью первого пользовательского пути.

---

### 2. Один пользователь = одно устройство

На старте:

```text
1 аккаунт
=
1 активная подписка
=
1 устройство
```

Не нужно сразу делать семейные тарифы, 3–5–10 устройств и т. д.

Нужно продумать простой способ:

- зарегистрировать первое устройство;
- не позволять бесконтрольно расшаривать одну подписку;
- при необходимости дать пользователю возможность заменить старое устройство новым.

---

### 3. Пользователь не должен разбираться в VPN

Нежелательный UX:

```text
получи длинный VLESS-ключ
→ скопируй его
→ открой INCY
→ найди Import
→ вставь
→ настрой что-то
```

Предпочтительный UX:

```text
скачай INCY
↓
вернись на наш сайт
↓
нажми «Подключить»
↓
INCY автоматически открывается
↓
наша подписка импортируется
↓
Connect
```

То есть хотим использовать deep-link / subscription URL INCY.

Ручное копирование ключа должно быть только fallback-сценарием:

**«Не получилось автоматически → скопировать ссылку вручную».**

Нужно сделать этот flow максимально коротким.

# Trial

Trial хотим оставить.

Параметры пока НЕ зафиксированы.

Рабочие гипотезы:

- 1–3 дня;
- небольшой лимит трафика;
- только одно устройство.

Нужно определить оптимальную механику trial с точки зрения:

- минимального friction;
- защиты от бесконечного создания новых trial;
- конверсии в оплату.

---

# Платная подписка

Пока рабочая гипотеза:

**~249–299 ₽ / месяц**

Но цену пока не считать окончательно принятой.

На MVP желательно иметь **один тариф**, а не строить сложную тарифную сетку.

Например:

```text
1 устройство
1 месяц
один понятный тариф
```

Годовые планы, семейные тарифы и сложные bundles пока не нужны.

---

# Реферальная механика

Хотим заложить рефералку уже в MVP.

Каждый пользователь получает ссылку:

```text
нашсайт.ru/r/ABC123
```

Друг:

```text
переходит по ссылке
↓
регистрируется
↓
получает trial
↓
покупает подписку
↓
срабатывает referral reward
```

Для обычных пользователей предпочтительнее **не деньги**, а дополнительное время подписки.

Рабочая гипотеза:

**пригласи друга → после его первой оплаты вы оба получаете +N дней.**

Нужно определить оптимальное N и правила против abuse.

Отдельную affiliate-программу:

```text
блогеры
→ %
→ баланс
→ выплаты
```

на MVP пока НЕ строим.

# Что находится под продуктом

На техническом уровне предполагаем примерно:

```text
Наш сайт
↓
наш backend
↓
users / payments / trials / referrals
↓
VPN control layer
↓
Xray
↓
VLESS + REALITY
↓
наши VPN-серверы
↓
INCY пользователя
```

### INCY

INCY = только пользовательский клиент.

Он:

- принимает нашу subscription URL;
- получает конфигурации;
- создаёт VPN-соединение.

### Xray

Xray-core = готовый open-source сетевой движок.

Мы НЕ собираемся самостоятельно писать:

- криптографию;
- собственный VPN-протокол;
- собственный Xray;
- собственное мобильное VPN-ядро.

### Протокол

Предварительный основной кандидат:

**VLESS + REALITY**

Но техническое решение окончательно будем принимать после продуктовой сборки.

# Remnawave — пока НЕ окончательное решение

Ранее рассматривали Remnawave.

Важно понимать:

```text
INCY
≠
Remnawave
```

INCY находится на телефоне пользователя.

Remnawave — возможный backend/control-plane для управления:

- VPN-пользователями;
- сроком доступа;
- subscription URL;
- нодами;
- трафиком;
- устройствами.

Но Remnawave НЕ является обязательным.

Альтернатива:

```text
наш backend
↓
напрямую управление Xray
```

Поэтому пока считать вопрос:

**Remnawave vs собственный минимальный control layer**

открытым.

Не выбирать Remnawave автоматически только потому, что он обсуждался раньше.

# Принцип разработки

Проект хотим собирать преимущественно через AI / vibe coding.

Поэтому архитектура должна быть:

- максимально простой;
- с минимальным количеством собственного инфраструктурного кода;
- без самописной криптографии;
- без собственного мобильного приложения на первом этапе;
- легко поддерживаться маленькой командой;
- позволять позднее заменить INCY собственным приложением без переписывания всей бизнес-системы.
